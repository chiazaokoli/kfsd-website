# Project guidance

## Goal

Build a polished Next.js landing page for the virtual soft skills training waitlist. The event takes place November 25–26, 2026, from 10:00 AM to 12:00 PM West Africa Time (UTC+1) each day.

## Mobile-first priority

- Mobile is the highest-priority experience for every design and implementation decision.
- Design for small screens first, then enhance the experience for tablets and desktops.
- Make mobile layouts, typography, imagery, navigation, forms, interactions, animation, accessibility, and performance feel complete and intentional rather than compressed versions of desktop.
- Prevent horizontal overflow, clipped content, crowded controls, unreadable text, awkward image crops, and overlapping elements at common mobile widths.
- Keep touch targets comfortable, primary actions easy to reach, forms simple to complete, and important content clear without relying on hover.
- After every meaningful visual or interaction change, verify the mobile production experience at multiple viewport widths and treat mobile defects as release blockers.

## Audience and tone

- Speak directly to high school, pre-college, and university students in Nigeria and internationally.
- Keep the experience modern, youthful, professional, welcoming, and accessible.
- Use clear language and connect soft skills to practical academic, career, and personal situations.

## Product priorities

- Make joining the registration waitlist the primary call to action.
- Clearly explain the program, intended participants, outcomes, schedule, time zone, and commitment.
- Build trust through real organizer, facilitator, testimonial, video, affiliation, and past-program evidence when supplied.
- Never invent credentials, testimonials, affiliations, impact figures, or program history.
- Use honest placeholders or omit unsupported claims until verified content is available.
- Design responsively and meet accessibility fundamentals, including semantic structure, keyboard usability, sufficient contrast, descriptive labels, and reduced-motion support.

## Working practices

- “Don't build” means inspect or discuss only: do not edit code or implement changes.
- Once the user gives the go-ahead to make changes, implement, verify, run the production build, and deploy to GitHub Pages so the changes are visible on the live site.
- Inspect the repository and preserve unrelated user changes before editing.
- Follow the project’s existing package manager, lockfile, scripts, conventions, and component patterns.
- Implement requested work end to end without pausing for routine decisions that can be inferred safely.
- Start the app and verify key user flows after meaningful changes.
- Run the relevant lint, type-check, test, and production-build commands that the project provides.
- Report completed work, verification results, and genuine blockers clearly.
